# 桌宠三大问题诊断与解决方案

> 状态：✅ 问题②③ 已实施（v2.4，2026-08-19）；问题① 按用户要求暂缓 · 方案制定于 2026-08-19
> 对应问题：① 安装包体积大（73.7MB，暂缓）② 运行偶发卡顿（已修）③ 置顶偶发失效（已修）
> 关联文件：main.js（窗口/置顶/调度）、renderer.js（事件监听/动画）、styles.css（动画/滤镜）、package.json（打包配置）、scripts/dist-temp.ps1（打包流水线）

## 0. 结论摘要

| 问题 | 根因（一句话） | 解决方向 | 预期收益 |
|---|---|---|---|
| ① 安装包 73.7MB | Electron 运行时本体税（Chromium+V8+Node 解压约 220MB，压缩后约 73MB），应用代码仅占 1.4MB（<2%） | 裁剪语言包 + 压缩参数调优；根本性缩小需换框架 | 降至约 65MB（换框架可到 10MB 级，但需重写） |
| ② 偶发卡顿 | 透明分层窗口持续合成 + 呼吸动画 3s 无限循环 + 拖动时高频 setBounds，在 GPU 争用/软件合成退化时 CPU 飙高 | 动画合成层优化 + 拖动 rAF 节流 + 阴影滤镜优化 | 拖动卡顿消除；待机 GPU 占用显著下降 |
| ③ 置顶失效 | TOPMOST 窗口之间 Z 序竞争（后来激活者盖住桌宠），桌宠无重提机制；层级不够高（floating） | 提升至 screen-saver 级 + 定时 moveTop 保活 + 全屏场景兜底 | 常规场景基本不再被盖 |

## 1. 问题一：安装包体积（73.7MB）

### 1.1 体积构成（实测）

| 构成 | 解压体积 | 安装包占比（估算） |
|---|---|---|
| Electron 31 运行时（Chromium + V8 + Node + dll/pak） | 约 220MB | 约 98% |
| 应用代码（app.asar，含 electron-store 依赖） | 1.4MB | 约 2% |
| 图标/元数据 | 忽略不计 | <1% |

结论：**安装包大小 ≈ Electron 框架税**。应用自身只占 2%，v2.3 的 chat.js 用 Node 内置 fetch（零新增依赖），代码侧已无优化空间。

### 1.2 优化方案（按成本排序）

**方案 A：裁剪语言包（低成本，推荐先做）**
- Electron 自带 50+ 种语言的 locale pak（约 25-30MB 解压）
- 在 `package.json` build 配置加：`"electronLanguages": ["zh-CN", "en-US"]`
- 预期收益：安装包约省 4-8MB

**方案 B：NSIS 压缩参数调优（低成本）**
- build 配置加 `"nsis": { "compression": "maximum" }`（默认 lzma solid，maximum 略增压缩率、稍增打包耗时）
- 预期收益：约省 2-4MB

**方案 C：升级 Electron 或降级对比（中成本，收益不确定）**
- 不同版本运行时体积略有差异，但总体趋势是**新版更大**（31→37 会增加）；不建议仅为体积升降级，需与问题二的 GPU 兼容性一起评估

**方案 D：换轻量运行时（高成本，不推荐本项目）**
- Tauri（Rust + 系统 WebView，安装包约 5-15MB）或 Neutralino——需整体重写
- 本项目定位是 vibe coding 课堂演示（Electron 教学项目），不建议改框架；若课程主题允许可作为二期议题

**方案 E：Web 安装包（低优先级）**
- electron-builder 的 web installer 初始下载小、安装时联网下载运行时——用户体验降级，不推荐

### 1.3 现实预期

- 方案 A+B 落地后：**约 73.7MB → 65MB 上下**
- Electron 桌面应用 70MB 级安装包是行业常态（同类应用普遍如此），**低于 60MB 需要换框架**，请按此设定预期

## 2. 问题二：运行偶发卡顿

### 2.1 嫌疑根因清单（按证据强度排序）

**① 透明分层窗口 + 无限呼吸动画 = 持续全窗合成（最大嫌疑）**
- `transparent: true` 让 Windows 走分层窗口（layered window）合成路径，成本高于普通窗口
- `.anim-idle { animation: breathe 3s ease-in-out infinite; }` 待机时**永不停止**地驱动重绘
- `#pet { filter: drop-shadow(...) }` —— filter 会在每帧重新光栅化阴影（滤镜不缓存）
- 平时 GPU 加速时开销尚可；一旦 GPU 被占用（视频/游戏）或驱动退化到软件合成，CPU 会持续被占 → 用户感知"电脑变卡"
- **卡顿"有时候"出现**，与 GPU 争用场景吻合

**② 拖动时高频 setBounds（拖动期间必然卡顿）**
- `document.addEventListener('mousemove')` → 每次鼠标移动都发一次 `window:drag-to` IPC → 主进程 `screen.getCursorScreenPoint()` + `dragWin.setBounds(...)`
- 鼠标事件频率可达 125-1000Hz，setBounds 是昂贵操作（窗口重定位 + 重合成），远超 60Hz 需求
- 表现为拖动宠物时画面/系统卡顿

**③ 穿透 forward 事件流（常驻开销）**
- `setIgnoreMouseEvents(true, { forward: true })` 把经过 560×560 窗口区域的所有鼠标移动事件转发给渲染层（这是 hover 检测的前提）
- 回调虽立即 return，但事件转发本身有 IPC 与 DOM 事件开销；窗口越大、鼠标越常经过，开销越大

**④ electron-store 同步 IO（低频，非主因）**
- `tick()` 每 10 秒 `store.get('reminders')`（electron-store 有内存缓存，get 不读盘）
- 写盘只在配置修改/拖拽结束/会话历史保存时发生（低频），非卡顿主因

**⑤ 高 DPI 屏 + force-device-scale-factor=1（中性）**
- factor=1 实际**降低**了光栅化分辨率，性能上是正向的；不构成卡顿

### 2.2 验证方法（实施前先复现定位）

1. 打开任务管理器 → 性能页 → 观察卡顿时刻 electron 进程的 CPU/GPU 占用
2. 对比实验：临时注释呼吸动画（或改成 10s）运行半天，观察卡顿是否消失
3. 拖动对比：按住宠物快速拖动，观察卡顿是否集中在拖动期间
4. 开关实验：命令行 `electron . --disable-gpu` 启动，若卡顿消失 → 确认是 GPU 合成/驱动问题

### 2.3 优化方案

**方案 A：拖动节流（高价值，先做）**
- renderer.js 的 mousemove 处理加 rAF 节流：一帧最多发一次 `dragTo`，把 setBounds 频率压到 60Hz 以内
- 预期：拖动流畅度立竿见影

**方案 B：动画合成层优化（中价值）**
- `#pet` 加 `will-change: transform`（提示合成器预建层，减少反复光栅化）
- 把 drop-shadow 从常驻 filter 改为动画暂停时移除/降低，或换为静态阴影方案（纯 emoji 原则下可评估去掉阴影或减淡）
- 呼吸动画时长 3s → 5-6s（降低重绘频率，视觉上更柔和）

**方案 C：空闲降载（可选）**
- 长时间无交互（如 30 分钟）后呼吸动画暂停/降频，鼠标悬停时恢复
- 注意：呼吸是桌宠"活着"的核心表现，需与用户确认

**方案 D：窗口尺寸按需收缩（可选，改动较大）**
- 待机时窗口保持 560×560 以支持气泡/面板展开；若改造为气泡弹出时动态 resize，待机可缩到宠物本体大小，合成面积降低约 80%——收益大但改动涉及布局，需评估

**方案 E：升级 Electron 评估 GPU 兼容（与问题一方案 C 联动）**
- Windows 25H2 上 Electron 31 的 GPU 合成偶发退化；升级到 37 可能改善，但运行时体积更大，需实测对比

## 3. 问题三：置顶偶发失效

### 3.1 机制与根因

Windows 的 TOPMOST 层级**没有绝对优先级**，多个置顶窗口并存时按激活顺序排 Z 序：

1. **Z 序竞争（最常见）**：其他应用启动/激活自己的置顶窗口（输入法候选窗、截图工具、视频小窗、任务管理器、音乐播放器悬浮窗等）后，会排在桌宠**上面**；桌宠没有任何重提机制，被盖住后不会自动回到最前
2. **层级不够高**：`alwaysOnTop: true` 默认是 `floating` 级；系统内存在更高层级 `screen-saver`（任务管理器等）可盖住 floating 级窗口
3. **独占全屏绕过**：游戏/视频的独占全屏模式绕过桌面合成器直接输出，任何置顶窗口都会被盖住（Windows 机制，无法通过置顶解决）
4. **系统场景重置**：锁屏/解锁、UAC 安全桌面、切换用户、显示器插拔后，窗口 TOPMOST 标志或 Z 序可能被系统重置
5. **穿透窗口无焦点**：`setIgnoreMouseEvents(true)` 时窗口不持有焦点，部分应用激活时会重新排列 TOPMOST Z 序

### 3.2 解决方案

**方案 A：提升置顶层级（一行改动）**
- 窗口创建后：`win.setAlwaysOnTop(true, 'screen-saver')`
- 预期：压过绝大多数普通置顶窗口

**方案 B：定时保活重提（核心方案）**
- 每 5 秒执行一次 `win.moveTop()`（只调 Z 序、不抢焦点、无闪烁），让桌宠始终回到 TOPMOST 最前
- 若 moveTop 不足以恢复，备用 `setAlwaysOnTop(false)` → `setAlwaysOnTop(true, 'screen-saver')`（注意可能有瞬时闪烁，作为保底）
- 开销：每 5 秒一次系统调用，可忽略

**方案 C：全屏场景兜底（可选）**
- 检测到独占全屏时无法置顶，可退化为：自动暂停置顶保活（避免无谓操作）或提示用户；此场景占比低，一期可仅记录不做

**方案 D：配置中心窗口同步处理**
- cfgWin 同样加 screen-saver 级 + 保活（它也是 alwaysOnTop）

### 3.3 风险与边界

- 定时 moveTop 不与"点击穿透"冲突（穿透只影响鼠标事件，不影响 Z 序）
- 用户正在桌宠面板里打字时 moveTop 只调 Z 序不抢焦点，输入不被打断（需实测确认）
- 与刻意盖住桌宠的应用（如用户主动把视频小窗放桌宠上面）存在"竞争"：保活会让桌宠持续回到最前——**可提供"暂停置顶"开关**（配置中心加一项），把选择权交给用户

## 4. 实施计划建议（按优先级）

| 阶段 | 内容 | 改动文件 | 验证方式 | 状态 |
|---|---|---|---|---|
| P0（问题③） | setAlwaysOnTop('screen-saver') + 5 秒 moveTop 保活 + 「始终置顶」开关 | main.js、preload.js、renderer.js、index.html、styles.css | 开多个置顶窗口（任务管理器/视频小窗）压盖桌宠，观察 5 秒内是否恢复最前 | ✅ 已实施（2026-08-19） |
| P1（问题②） | 拖动 mousemove rAF 节流 | renderer.js | 拖动观察帧率/卡顿对比 | ✅ 已实施（2026-08-19） |
| P1（问题②） | #pet 加 will-change + 呼吸动画 3s→5s + 阴影减负 | styles.css | 任务管理器 GPU/CPU 占用对比；--disable-gpu 对比实验 | ✅ 已实施（2026-08-19） |
| P2（问题①） | electronLanguages 裁剪 + nsis compression maximum | package.json、scripts/dist-temp.ps1（如需） | 重新打包对比安装包大小 + 纯净校验仍通过 | ⏸ 暂缓（用户指示） |
| P3（可选） | 空闲降载 / 窗口按需收缩 / Electron 版本评估 | 多文件 | 逐步实测 | 未启动 |

**已实施验收**（v2.4）：① 拖动经 rAF 节流后一帧最多一次 setBounds（60Hz 内）；② 待机呼吸动画 5s + will-change 合成层预建 + 阴影减负；③ 置顶提升至 screen-saver 级，每 5 秒 moveTop 保活，配置中心新增「始终置顶」开关（关闭时降级普通窗口并停止保活）；三文件语法检查通过 + npm start 冒烟无报错。**待用户实测**：任务管理器观察 CPU/GPU 占用、多置顶窗口压盖场景 5 秒恢复、拖动流畅度、开关交互。

**验收总标准**：① 安装包体积有可量化下降且功能不回归（暂缓）；② 拖动流畅、待机 GPU 占用下降且呼吸动画视觉可接受；③ 常规多置顶窗口场景下桌宠 5 秒内回到最前，打字/拖动交互不被打断。

## 5. 风险提示

- 置顶保活与"用户想让其他窗口盖住桌宠"的需求存在天然冲突 → 必须提供开关
- Electron 升级可能引入新兼容问题且体积变大 → 需实测对比后再定
- 换框架（Tauri 等）收益最大但违反项目 Electron 教学定位 → 仅作备选记录
- 所有性能优化必须以"待机 0 交互时不抢 CPU/GPU"为目标，避免优化引入新的常驻开销
