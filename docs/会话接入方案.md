# 会话能力接入方案（复用 deepseek-harness）

> 状态：✅ 方案 A 已实施（v2.3，2026-08-19） · 设计稿生成于 2026-08-19
> 关联：需求规范 §2.5/§3 交互面板、技术规范 §5.5 大模型会话后端、开发日志 v2.3
> 实施备注：按用户要求**未改动 deepseek-harness**（仅参考设计，后续可删除）；复刻设计要点落地于 `chat.js`（纯 Node 流式后端），.env 填 `DEEPSEEK_API_KEY` 即用；本方案其余路径（B/C/D）仅作备选未实施。

## 1. 背景与目标

**现状**：交互面板的 `sendChat()`（renderer.js）是占位实现——用户消息入气泡后，固定回复"（大模型 agent 接入中…）"。需求规范已预留"大模型 agent 接入"位。

**目标**：让桌宠具备真实多轮对话能力（流式输出、历史记忆、人设），并最大化复用 `deepseek-harness`（已放入项目文件夹）中已完成的内容。

**范围**：本方案只做设计，不实施。

## 2. 调研结论

### 2.1 harness 是什么

- DeepSeek 开源的 **Cordis 插件化编码 agent 框架**（v0.1.0-rc.7，MIT 协议）。
- 处于 **developer preview**：README 明示"将会有破坏性兼容变更"。
- 工程要求：Node `^22.19.0 || >=24.0.0`、pnpm 11 的 monorepo；**当前目录未安装依赖、未构建**（无 node_modules、无 lib）。
- 桌宠 Electron 31 内置 Node 20，**不满足** harness 运行时要求 → harness 进程不能嵌入 Electron，只能作为系统 Node 启动的独立子进程。

### 2.2 一句话结论

能复用，但要分清两个层次：

| 层次 | 含义 | 成本 |
|---|---|---|
| **复用实现** | 把 harness 当独立进程跑（ACP / headless / web），复用整套 agent 引擎 | 高（构建、分发、运行时耦合） |
| **复用设计/协议** | 借鉴它的 LLM 端点约定、消息结构、提示词组织，在桌宠内轻量自实现 | 低 |

桌宠的会话是**陪伴聊天**，不是编码任务。harness 引擎里最重的部分（bash/fs/subagent/todo 工具栈、沙箱、权限策略）对陪伴聊天是负资产；真正需要的部分（DeepSeek 调用、多轮历史、系统提示词）本身很薄。因此推荐：**以"复用设计"为主线落地（M1/M2），以"复用实现"（ACP sidecar）为可选进阶（M3）**。

## 3. 可复用内容盘点

| harness 资产 | 对桌宠会话的价值 | 复用方式 | 成本 |
|---|---|---|---|
| `dsh-llm-deepseek` 适配器 | **高**——OpenAI 兼容端点（`DEEPSEEK_BASE_URL`/`DEEPSEEK_API_KEY`）、流式协议、模型名约定 | 参考实现：主进程用 Node 内置 fetch 直连，约百行 | 极低 |
| `Message`/`ContentBlock` 消息结构 | 中——`role`/`content`/`source` 通用约定 | 借鉴结构存历史，未来可平滑映射到 ACP | 低 |
| `ContextForm 'catalog'` 概念 | 中——"当前可用项目录"作为动态上下文注入提示词 | 借鉴思想：把用户常用命令列表注入人设 | 低 |
| system-prompt 分段组装 | 中——persona + 动态上下文分离 | 简化为固定人设 + 时间/命令目录两段 | 低 |
| 会话日志（JSONL 追加式） | 中——多轮历史持久化 | 桌宠用 electron-store 存历史（结构对齐） | 低 |
| 上下文压缩 compaction | 低～中——长聊后裁剪 | 先做"保留最近 N 轮"，摘要压缩后续参考 | 低 |
| agent loop + 工具栈 | 低——编码向，陪伴聊天不需要 | 不复用（除非 M3 想要 agent 型桌宠） | — |
| **ACP stdio 通道** | 中——官方"程序化客户端"接口 | M3 可选：spawn 常驻 ACP 进程，JSON-RPC 通信 | 高（见 §4 方案 B） |
| headless 一次性任务 | 低——无记忆、无流式、冷启动慢 | 不采用 | — |
| `dsh web` + `/api` HTTP 桥 | 低——需常驻服务 + Typert 严格生成合同 | 不采用 | — |

**要点**：直接可用（可运行）的通道只有 ACP/headless/web 三条；其中只有 ACP 适合"程序化客户端"身份，但存在硬伤（见下）。

## 4. 接入方案对比

### 方案 A：直连 DeepSeek API（复用设计）★ 推荐

Electron 主进程用 Node 内置 `fetch` 调 `POST {baseUrl}/chat/completions`（SSE 流式），IPC 把 chunk 逐字推给渲染层。

- **优点**：真逐字流式（聊天体验的核心）；零外部进程、零新依赖；打包体积不变；故障面小、可控。
- **缺点**：不运行 harness 代码（复用停留在协议/设计层面）；历史与错误处理需自实现。

### 方案 B：ACP sidecar（复用实现）— M3 可选

主进程 spawn 常驻 ACP 服务器（系统 Node 跑 harness），stdio JSON-RPC：`session/new` → `session/prompt` → `session/update`。

- **优点**：复用全套引擎（会话、工具、压缩、权限策略）；将来可升级成"能执行命令/读文件"的 agent 型桌宠。
- **缺点**：
  1. **无逐 token 流式**——`session/prompt` 只交付"已提交消息"（协议明确以逐字延迟换干净结果），聊天时整段等待，体验差；
  2. **只支持新建会话**——无 load/resume，桌宠重启即失忆，违背"记忆"预期；
  3. **构建门槛高**——需系统 Node 22+、pnpm install + build 整个 monorepo；分发需捆绑 Node 运行时 + 构建产物；
  4. developer preview 破坏性变更无保证。

### 方案 C：dsh web sidecar — 不推荐

需用户常驻运行 `dsh web`（127.0.0.1:3080）；宠物侧要装配 Typert 生成的严格客户端合同（`dsh-api-remotes` client 端），对 Electron 工程耦合极深，且"双击即聊"的桌宠不该依赖一个外部常驻服务。

### 方案 D：headless 每次拉起 — 不推荐

每条消息冷启动一个进程、每次新建会话（无记忆）、输出非流式。最不适合聊天场景。

### 对比总表

| 维度 | A 直连 | B ACP sidecar | C web sidecar | D headless |
|---|---|---|---|---|
| 流式体验 | ✅ 逐字 | ❌ 整段等待 | ✅ | ❌ |
| 多轮记忆 | ✅ 自管 | ⚠️ 仅内存（重启失忆） | ✅ | ❌ |
| 复用 harness 程度 | 设计/协议 | 全套引擎 | 全套引擎 | 全套引擎 |
| 部署复杂度 | 极低 | 高 | 高 | 中 |
| 风险 | 低 | 高（预览版+构建） | 高 | 高 |

### 推荐

**M1/M2 采用方案 A，并把主进程"模型后端"抽象成可替换接口（`ChatBackend`），为 M3 的 B 预留架构位。** 方案 B 只在"想要能干活（执行命令/读写文件）的 agent 型桌宠"时才值得启动。

## 5. 推荐方案设计（方案 A）

### 5.1 总体架构

```
渲染层 renderer.js                    主进程                    外部
┌──────────────────┐   IPC invoke    ┌────────────────────┐
│ sendChat(text)   │ ──────────────▶ │ chat.js（新增）    │
│ onChatChunk(cb)  │ ◀── webContents  │  请求组装/SSE 解析  │ ──fetch──▶ DeepSeek
│ onChatDone/Error │     .send 推送   │  历史管理/错误降级  │ ◀─SSE 流── OpenAI 兼容端点
└──────────────────┘                 └────────────────────┘
preload.js 白名单新增 5 个通道          electron-store:
                                      settings.chat { apiKey, baseUrl, model, systemPrompt }
                                      chat.history[]（最多 N 轮）
```

### 5.2 主进程 `chat.js` 职责

- **请求组装**：`messages = [system(人设)] + history(最近 N 轮) + [当前消息]`。
- **流式调用**：`fetch(baseUrl + '/chat/completions', { stream: true })`，逐行解析 SSE delta，`win.webContents.send('chat:chunk', { delta })`。
- **中止**：`AbortController` + `chat:abort`——关闭面板/新消息到来时中断旧请求。
- **历史落盘**：本轮问答完成后追加进 `chat.history`，超出 N 轮裁掉最旧（N 默认 10，可配置）。
- **错误降级**：无 apiKey 或请求失败 → 走 `chat:error`，渲染层回退到现有占位回复文案，离线不崩。

### 5.3 IPC 设计（preload.js 白名单新增）

| 通道 | 类型 | 说明 |
|---|---|---|
| `chatSend(text)` | invoke `chat:send` | 发起一轮对话，返回是否受理 |
| `chatAbort()` | send `chat:abort` | 中止当前流式请求 |
| `onChatChunk(cb)` | on `chat:chunk` | 收到一段 delta |
| `onChatDone(cb)` | on `chat:done` | 本轮完成（含落盘后的完整消息） |
| `onChatError(cb)` | on `chat:error` | 出错（渲染层降级为占位回复） |

流式推送沿用现有 `reminder:trigger` / `data:changed` 的 `webContents.send` 模式。

### 5.4 渲染层改造（renderer.js）

- `sendChat()`：先 `addChatMessage(text, 'user')`，再开一个空的 bot 气泡，逐 chunk 追加文本（`chat:chunk`）；输入中禁用发送按钮，`chat:done`/`chat:error` 后恢复。
- 高频 chunk 需节流：按帧（requestAnimationFrame）批量 append，避免逐字触发重排卡顿。
- 问候语逻辑不变；关闭面板时若请求未完成，调用 `chatAbort()`。

### 5.5 配置中心新增"大模型"卡片

- 字段：**API Key**（密码框）、**Base URL**（默认 `https://api.deepseek.com`，与 harness `DEEPSEEK_BASE_URL` 同协议）、**模型**（`deepseek-chat` / `deepseek-reasoner`）、**系统提示词**（人设文本，默认沿用现有问候语气）。
- 存储：electron-store `settings`（位于 `%APPDATA%`，与现有配置一致，永不进包）。
- 同步：复用 `data:changed` 广播（改配置即时生效，无需重启）。

### 5.6 记忆与人格

- **历史结构参考 harness `Message`**：`{ role: 'user'|'assistant', content }`，为将来映射 ACP 会话留接口。
- **人设注入借鉴 harness `ContextForm 'catalog'` 思想**：把用户常用命令列表（配置中心 `commands`）作为"可用项目录"注入系统提示词，宠物可以"知道"并推荐用户配置过的命令，形成产品联动。

## 6. 工程约束联动（实施时必须同步）

1. **打包白名单**：新增 `chat.js`（或拆分文件）后，`package.json` 的 `build.files` 与 `scripts/dist-temp.ps1` 的 asar 校验白名单必须同步加入，否则打包/纯净校验双失败。
2. **harness 不进包**：`build.files` 白名单已天然挡住 `deepseek-harness/`；建议 `.gitignore` 增加 `deepseek-harness/` 与 `.env`（harness 的 API Key 根约定文件），避免误提交误打包。
3. **API Key 安全**：electron-store 明文存 `%APPDATA%`（与现有个人配置同策略、不进包），需在文档与配置界面标注风险；不得写入日志。
4. **网络**：直连 DeepSeek 需外网可达；有代理需求的用户按环境自行处理（桌宠不内置代理配置，避免复杂度）。
5. **纯净性校验继续通过**：个人数据全部留在 `%APPDATA%`，包内仍只有白名单代码文件。

## 7. 分阶段实施计划

| 里程碑 | 内容 | 验收要点 |
|---|---|---|
| **M1 对话打通** | chat.js + IPC 五通道 + 渲染层流式渲染 + 配置中心"大模型"卡片 | 配好 Key 后双击→输入→逐字流式回复 |
| **M2 记忆与人格** | 历史 N 轮上限、系统提示词人设、常用命令 catalog 注入、错误降级打磨 | 多轮上下文连贯；重启后历史仍在；断网降级占位回复 |
| **M3 可选：agent 型桌宠** | 按方案 B 接 ACP sidecar | 前置条件：系统 Node 22+、harness 完成 pnpm install+build；需接受"整段等待、无会话恢复"的体验妥协 |

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| harness developer preview 破坏性变更 | 方案 A 不依赖 harness 运行；M3 若接入需锁定 commit/版本 |
| API Key 明文存储 | 与现有配置同策略存 `%APPDATA%` + 文档风险提示；后续可换 Electron `safeStorage` 加密 |
| 高频流式渲染卡顿 | chunk 按帧节流批量 append |
| 断网/欠费/接口异常 | `chat:error` 降级占位回复，不崩溃、不丢用户体验 |
| 长对话 token 溢出 | 历史轮数上限；后续参考 harness compaction 做摘要压缩 |
| 打包回归 | 白名单联动检查纳入验收清单 |

## 9. 验收标准（M1/M2）

1. 配置中心填入 API Key/模型后，双击宠物 → 输入 → 收到逐字流式回复，多轮上下文连贯。
2. 无 Key 或断网时回退占位回复，应用不崩溃。
3. 关闭面板或连续发送时，旧请求被正确中止，无串话。
4. 历史轮数上限生效；重启应用后历史仍在。
5. 常用命令以 catalog 形式进入人设上下文（宠物能推荐用户配置的命令）。
6. 一键打包通过，asar 纯净校验通过（包内无 Key、无 harness、无个人数据）。
7. 双窗口（宠物/配置中心）回归无影响，`npm start` 全功能正常。
